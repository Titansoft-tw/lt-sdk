# LtErrorGuard (#9)

The iOS twin of `lt-error-guard-android` (#7): same rules, same vectors, same API shape. No dependencies.

```swift
let guardian = ErrorGuard(rules: .default, sink: { first in /* app_error with first.domain / code / count */ })
let rules = try GuardRules.parse(json)        // throws GuardRulesError (problems: [String])
guardian.decide(GuardEvent(exceptionTypes: ["NSURLErrorDomain"]))
let totals = guardian.endSession()
```

**Remote rules** (`lt-error-guard-spec` README "Remote rules"), same behaviour as Android; `refresh()` is async:

```swift
let loader = try GuardRulesLoader(guard: guardian, url: URL(string: "https://cdn.example.com/guard/ios.json")!,
                                  publicKey: guardRulesPublicKeyPEM, cacheFile: cachesDir.appendingPathComponent("guard-rules.json"),
                                  onApplied: { v in SentrySDK.configureScope { $0.setTag(value: "\(v)", key: "guard_rules_version") } })
loader.applyCached()                     // at start, before Sentry sends anything
let periodic = loader.startPeriodic()    // refresh now and every 6 h; periodic.cancel() stops it
```

Signatures are checked with CryptoKit (`P256.Signing`). `guardian.updateRules(rules)` is there for apps that load rules
their own way.

`ErrorGuard` is `Sendable` (an `NSLock` inside); the sink runs outside the lock. `DefaultRules.swift` is generated by
`lt-error-guard-spec/generate.js`.
